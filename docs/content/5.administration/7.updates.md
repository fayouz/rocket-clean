## Version installée

La version s'affiche en bas du menu, pour tous les utilisateurs. Les administrateurs y voient un badge **Nouveau** quand une version plus récente est publiée ; un clic ouvre **Administration → Mises à jour**.

La version vient de l'image Docker : la CI y inscrit le résultat de `git describe --tags`.

| Affichage | Signification |
|---|---|
| `0.7.0` | Version publiée (tag `v0.7.0`) |
| `0.7.0+3 (abc1234)` | 3 commits après la version 0.7.0, par exemple une image de `develop` |
| `dev` | Build local, sans version : il n'est pas comparé aux versions publiées |

## Nouvelles versions

La page **Mises à jour** compare la version installée à la dernière version publiée sur GitHub :

- les *releases* du dépôt (hors brouillons et préversions), avec leurs notes ;
- à défaut, les tags `vX.Y.Z`.

La vérification est faite au plus une fois par heure (l'API anonyme de GitHub est limitée) ; **Vérifier maintenant** la force. Pour suivre un autre dépôt (un fork), changez `UPDATE_REPOSITORY` ; videz-la pour ne jamais contacter GitHub.

## Choisir la méthode

Dans **Mises à jour**, la carte **Méthode de mise à jour** propose trois méthodes, selon l'installation :

| Méthode | Installation | Le bouton « Mettre à jour »… |
|---|---|---|
| **Docker (Watchtower)** | Docker Compose, images de ghcr.io | demande à Watchtower de télécharger les nouvelles images et de redémarrer les conteneurs |
| **Serveur sans Docker (script)** | `git clone`, PHP, Node, services systemd | demande à la tâche planifiée de lancer `deploy/update.sh` |
| **Manuelle** | toutes | n'existe pas : la page donne les commandes à lancer |

Le choix est enregistré en base. Par défaut, c'est `UPDATE_METHOD`, ou à défaut Docker si `UPDATER_TOKEN` est défini, sinon manuelle. Chaque mise à jour est gardée dans l'**historique** : date, auteur, versions, résultat.

## Avec Docker

1. Rocket Clean demande la mise à jour à Watchtower, par son API HTTP protégée par un jeton ;
2. Watchtower télécharge les nouvelles images des conteneurs `api`, `worker` et `front`, puis les redémarre ;
3. l'API applique les migrations à son démarrage ;
4. la page attend que la nouvelle version réponde, puis se recharge.

Rocket Clean est indisponible une à deux minutes.

::steps{level="3"}

### Utiliser les images publiées

Watchtower met à jour des images qu'il peut télécharger : celles de GitHub Container Registry, pas celles construites sur le serveur (`--build`).

```bash [.env]
API_IMAGE=ghcr.io/fayouz/rocket-place-api:latest
FRONT_IMAGE=ghcr.io/fayouz/rocket-place-front:latest
```

`latest` suit la branche `main`, c'est-à-dire les versions publiées. Un tag comme `0.7` suit les correctifs d'une version.

### Choisir un jeton

Un secret partagé entre l'API et Watchtower :

```bash [.env]
UPDATER_TOKEN=un-long-secret-aléatoire
```

### Démarrer avec le profil `updater`

```bash [Terminal]
docker compose --profile updater up -d
```

::

Watchtower ne touche qu'aux conteneurs portant le label `com.centurylinklabs.watchtower.enable=true` (ceux de Rocket Clean), et ne fait rien tout seul : il attend qu'un administrateur clique.

::warning
Watchtower accède au socket Docker : il peut piloter tous les conteneurs du serveur. Ne publiez pas son port, et gardez `UPDATER_TOKEN` secret.
::

::note
Si vos images sont privées sur ghcr.io, Watchtower doit pouvoir s'y connecter : montez le fichier `~/.docker/config.json` d'un `docker login ghcr.io` dans le conteneur (`/config.json`).
::

## Sans Docker

Pour une installation par `git clone` du dépôt (PHP 8.4, Composer, Node 22, PostgreSQL). Le serveur web ne lance jamais la mise à jour lui-même : il l'**enregistre**, et une **tâche planifiée**, qui tourne sous l'utilisateur propriétaire des fichiers, la lance dans la minute.

Le script `deploy/update.sh` :

1. vérifie qu'il n'y a pas de modification locale, puis récupère les tags du dépôt ;
2. passe sur le tag de la version (`TARGET_VERSION`, sinon le dernier tag `vX.Y.Z`) ;
3. installe les dépendances de l'API (`composer install --no-dev`) et construit l'interface (`npm ci`, `npm run build`) ;
4. applique les migrations et vide le cache ;
5. arrête les workers d'impression (leur superviseur les relance) et lance `UPDATE_RESTART_COMMAND`.

Si une étape échoue **avant les migrations**, il remet la version précédente. La page suit la mise à jour en direct (journal du script) et se recharge à la fin.

::steps{level="3"}

### Ajouter la tâche planifiée

Dans la crontab de l'utilisateur propriétaire des fichiers (`crontab -e`) :

```bash [crontab]
* * * * * cd /srv/rocket-place/backend && php bin/console app:update:run
```

La page **Mises à jour** indique si la tâche tourne (dernier passage).

### Redémarrer les services

L'API (PHP-FPM ou FrankenPHP) et l'interface (`node .output/server/index.mjs`) doivent redémarrer pour charger la nouvelle version :

```bash [.env.local]
UPDATE_RESTART_COMMAND="sudo systemctl restart rocket-place-front php8.4-fpm"
```

Avec `sudo`, autorisez seulement cette commande à l'utilisateur, sans mot de passe (`/etc/sudoers.d/rocket-place`) :

```text [sudoers]
www-deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart rocket-place-front php8.4-fpm
```

### Choisir la méthode

Administration → Mises à jour → **Serveur sans Docker (script)**, ou `UPDATE_METHOD=script`.

::

Le script se lance aussi à la main :

```bash [Terminal]
TARGET_VERSION=v0.7.0 deploy/update.sh
```

::note
L'interface est déployée ailleurs ? `UPDATE_BUILD_FRONTEND=0`. Binaires particuliers : `PHP_BIN`, `COMPOSER_BIN`, `NPM_BIN`. Autre remote git : `UPDATE_GIT_REMOTE`.
::

## Mettre à jour à la main

Avec la méthode **Manuelle**, la page affiche les commandes :

```bash [Terminal]
# Docker
docker compose pull
docker compose up -d

# Sans Docker
TARGET_VERSION=v0.7.0 deploy/update.sh
```

## Configuration

| Variable | Rôle | Défaut |
|---|---|---|
| `UPDATE_REPOSITORY` | Dépôt GitHub dont les versions sont consultées. Vide : pas de vérification. | `fayouz/rocket-place` |
| `UPDATER_URL` | API HTTP de Watchtower | `http://updater:8080` |
| `UPDATER_TOKEN` | Jeton partagé avec Watchtower. Vide : pas de mise à jour en un clic. | — |
| `UPDATE_METHOD` | Méthode par défaut : `docker`, `script` ou `manual` (les administrateurs la changent dans la page) | automatique |
| `UPDATE_SCRIPT` | Script de la méthode sans Docker | `deploy/update.sh` |
| `UPDATE_RESTART_COMMAND` | Commande lancée par le script pour redémarrer les services | — |
| `UPDATE_SCRIPT_TIMEOUT` | Durée maximale du script (secondes) | `1800` |
| `APP_VERSION` | Version de l'image, fixée à la construction (argument `APP_VERSION`). Sans Docker : fichier `backend/VERSION` écrit par le script. | `dev` |

API : `GET /api/system/version` (tout utilisateur connecté) ; pour les administrateurs, `GET /api/system/update` (`?refresh=1` pour forcer la vérification), `PUT /api/system/update/method`, `POST /api/system/update` et `POST /api/system/update/cancel` (mise à jour en attente de la tâche planifiée).
